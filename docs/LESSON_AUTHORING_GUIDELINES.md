# 教材作成ガイドライン v1

SfQC の解説と演習は、このガイドラインに沿って作成・改稿する。旧ガイドライン（`LESSON_AUTHORING_GUIDELINES_V0.md`）は使わない。

このガイドラインは、実装済みの2単元をもとにしている。
- 「基本統計量」（`descriptive-statistics`）：計算が中心の教材
- 「データの種類」（`data-types`、Issue #113 / PR #124）：判断・分類が中心の教材

迷ったときは、この2単元の実装（`src/lesson-registry.mjs`、`src/lesson-exercise-adapters.mjs`、`src/descriptive-statistics-*.mjs`）を見本にする。ただし、2単元にもこのガイドラインを満たしていない箇所がある（付録 C）。見本と規則が食い違うときは、規則を優先する。

---

## 1. 基本方針

1. **学習者が自分で判断できるようにする。** 用語の定義や分類の結果を覚えさせるのではなく、未知のデータにも使える判断の手順を教える。
2. **1つの例を最後まで使う。** 導入で示した共通の例を、各節で読み直す形にする。対照例やシミュレーションを足すのはよいが、共通の例を軸にする。
3. **正確さは「もっと正確に」に分ける。** 本文は初学者が読み通せる説明にする。記号、適用条件、例外は折りたたみの補足に置く。本文では、補足を読まなくても誤りにならない書き方をする。
4. **演習は問題単独で成り立たせる。** 本文を読まなくても、演習カードの中だけで解けるようにする。
5. **項目の強さは、次の4つの印で示す。** 文末の言い回しでは判断しない。
   - **【必須】**：全単元で守る。チェックリストの項目もすべて【必須】。外れてよいのは、その項目に書いた例外だけ。
   - **【推奨】**：外れてよい。外れるときは、理由と代わりにしたことを PR に書く。
   - **【許容】**：理由を書かずに使ってよい変形。ただし、【必須】の要素を消すものには使えない。
   - **例：**：見本。他の単元にそのまま写さない。
   印のない文は、次のように読む。
   - 印のある項目の下に書いた文：その項目の説明として、同じ強さで読む。
   - 印のある項目がない章・節の文（3章、4章、8章など）：【必須】として読む。
   - 「原則」と書いた文：【推奨】として読む。

## 2. 教材の構成

### 2.1 必須の要素と推奨の並び

【必須】教材には、次の要素を入れる。省けるのは、下の「省略できる場合」に書いた場合だけ。

| 要素 | 内容 |
|---|---|
| 導入 | 導入の問い、単元で共通に使う例、各節で確かめることの予告 |
| 節 | 2〜4節。各節に問いかけ、問いに答える材料（表・式・図）、説明、演習 |
| 補足 | 記号・適用条件・例外が要る節には「もっと正確に」 |
| 出典 | `references` |

省略できる場合：
- 「もっと正確に」：記号・適用条件・例外のどれも要らない節では省ける。
- 節ごとの演習：その節の内容を、次の節の演習でまとめて確かめる場合は省ける。どの演習で確かめるかを PR に書く。

【推奨】節の中の並びは、次のとおりにする。

```
問いかけ → 表・式・図 → 説明 → もっと正確に → 演習
```

【許容】次の変形は、理由を書かずに使ってよい。
- 式と説明を交互に置く（途中式ごとに意味を述べる）
- 節の冒頭に、観測単位などの前置きを1段落置く
- 要約表を、説明のあと（演習の前でも後でもよい）に置く
- 演習の前に、演習の進め方（事例の切り替えなど）を1段落で案内する
- 「もっと正確に」を、内容の分かる見出しにする（例：「n − 1 で割ると母分散に合うのか確かめる」）。1つの節に複数置いてもよい
- 共通の例に加えて、対照例やシミュレーションを置く

これ以外に並びを変える場合は【推奨】から外れるので、理由を PR に書く。

### 2.2 導入（overview）

- **導入の問いは、場面が浮かぶ書き方にする。** 状況を述べてから疑問を出す。
  - 良い例：「検査で基準を超える傷が3件見つかりました。しかし不適合品は2個です。なぜでしょうか？」
  - 避ける例：「基準を超える傷が3件あるのに、不適合品はなぜ2個なのでしょう。」（前提が唐突に感じられる）
- 共通の例は、各節で読み直せる大きさにする（目安は10行以内）。同じ値の行をまとめて表示する場合は、そのことを本文に書く（例：「D〜Jは7製品分の記録を1行にまとめて表示しています」）。
- 最後の段落で、各節で何を確かめるかを**全節について**順に予告する。

### 2.3 節の分け方

- 1つの節では、1つの考え方を扱う。
  - 例：基本統計量は「平均／偏差／範囲と分散／標準偏差」、データの種類は「観測単位／不適合数と不適合品数／計量値・計数値・カテゴリ」に分けた。
- 節は、前の節の結果を次の節で使う順に並べる。
- 各節に演習を1つ置く（`exerciseSlot`）。その節で扱った判断や手順を確かめる演習にする。2.1 節の「省略できる場合」に当たる節は除く。
- `sectionId` は、内容を表す英語の kebab-case にする（例：`observation-unit`）。

### 2.4 前提と参照

- 特定の技能が前提のときは、節で指定する（例：`data-types#types`、`math-algebra-sigma#sigma`）。
- 単元全体が前提のときと、前提の単元に収録済みの節がないときは、単元で指定してよい（例：`math-ratios-percentages`）。
- 復習リンク（`reviewSectionRefs`）は、常に節で指定する。
- 公式出題範囲との対応は、`sourceItemIds` と、そこから導く `sourceRefs`（台帳は `sources`。資料 ID・版・確認日・該当ページを持つ）で管理する。学習者向けの出典は `references` に書く（7章）。2つは用途が違うので、片方で代用しない。
- 節・前提・出題範囲の対応を変えたら、カリキュラム表（`docs/curriculum/`）と registry を一緒に直し、照合のテストを実行する。テストを書き換えるのは、照合の方法を変えるときと、テストが使う固定の事例や期待値（例：負例に使う前提の参照先、`curriculumRevision` の期待値）が、意図した変更で変わるときだけ。

### 2.5 計算中心の教材と判断中心の教材

| | 計算中心（基本統計量） | 判断中心（データの種類） |
|---|---|---|
| 説明の軸 | 手順と式（`formula`）。途中式を省かない | 判断の順序。分類の結果ではなく、どう判断するかを示す |
| 図（図を使う場合の推奨。使うかどうかは4章に従う） | 値を動かして変化を見る図 | 判断フロー図 |
| 演習 | 計算の結果を問うときは数値入力を原則とする。概念の比較、単位の判断、誤計算の診断は選択式でよい | 選択式。固定問題と、切り替えられる事例を組み合わせる |
| 問題の数 | パラメータを変えて多数生成する | 固定問題と、対照になる少数の事例 |
| 誤答説明 | 誤りの原因を特定できる場合は、どの計算手順を誤ったか。特定できない場合は 5.4 節に従う | どの判断（観測単位・集計対象・分類）を取り違えたか |

## 3. 本文の書き方

### 3.1 概念の定義

- **概念は、表の形や実装の形式に頼らずに定義する。** 先に対象や操作を決め、その結果として記録や表の形が決まる、という順序で書く。
  - 避ける例：「表の1行を1観測といいます。」（行をまとめて表示した表と矛盾する）
  - 良い例：「データを記録するときには、まず何を一つの観測対象とするかを決めます。この一つ分の対象を観測単位といいます。」
- 分類を教えるときは、**判断の軸を示す**（例：「その値は種類・判定を表すか、数量を表すか → 数量なら、測ったものか、数えたものか」）。分類の結果を並べた表だけで済ませない。
- 同じ値でも段階によって意味が変わる場合は、その違いを示す（例：製品ごとの 0/1 は記録の段階ではカテゴリ、集計した「2個」は計数値）。
- 式の結果のうち、判断や解釈が変わる値・場合は、本文で触れる（例：偏差の式に 0 が出たら、正・負だけでなく 0 の意味も述べる）。与えられた入力の値を言い直す必要はない。

### 3.2 条件と言い切り

- 「必ず」「常に」「〜にならない」「〜が変わる」と言い切る前に、反例がないかを確かめる。
  - 例：「傷明細を合計しても不適合品数にならない」は誤り。明細の行数と不適合品数が偶然一致する場合がある。正しくは「一致するとは限らない。1製品に複数の傷があると重複して数え、多くなる」。
  - 例：「取り出す標本が変わると、値も変わる」は誤り。異なる標本でも同じ値になることがある。正しくは「変わりうる」。
- 条件付きで成り立つことは、条件を先に書く。条件を満たす代表的な方法は、条件そのものと分けて書く。
  - 例：「0/1の合計は常に、集計した行にある1の個数です。検査全体の不適合品数として使うには、各不適合品が過不足なく1回ずつ1として現れる必要があります。全製品を1製品1行で記録すると、この条件を満たせます。」
- 確率・推定の主張では、抽出の条件（復元か非復元か、独立か、母集団の定義）を書く。期待値の性質と、1回ごとの値や有限回の試行の結果を区別する。
  - 例：シミュレーションは「試行を重ねると、平均がどう近づくかを観察する」ものとして書く。「くり返して平均すると一致する」とは書かない。
- 誤りの原因が複数あって打ち消し合う場合（記録漏れと重複など）は、「もっと正確に」で触れる。

### 3.3 用語・単位・表記

- 用語は単元の中で1つに統一する（例：「基準を超えた傷」）。似た言葉で言い換えない。
- 似た量は単位で書き分ける（例：不適合は「件」、不適合品は「個」）。
- 識別子（製品番号など）は、本文・表・選択肢・解説で同じ表記にする（例：`P-01`）。表が数値しか持てないからといって「1」「3」と書かない（8章）。
- **数量**には単位を付ける（`mm`、`mm²`、`件`、`個`）。単位は、値ごとに付けても、列見出しや式全体にまとめて示してもよい。コード（0/1）、個数を表す記号（`n`、`n − 1`）、識別子、単位のない量（相関係数など）には付けない。
- 二乗した量を扱うときは、元の単位と二乗した単位を区別して示す。

### 3.4 表

- キャプションで、何を記録した表かを示す。解説用の表では、1行が何を表すかも書いてよい（例：「（1行＝傷1件）」）。演習の表の扱いは 5.2 節に従う。
- 数量のセルは右寄せにする。
- 狭い画面では横スクロールで読めるようにする。
- 図の中の数表にも、キャプションか、何の表かが分かる説明を付ける。

## 4. 図

- 図は、学習者の判断や理解を助ける場合にだけ使う。装飾のための図は使わない。
- **図はコードで描く。** 画像ファイルや生成画像は使わない。
  - 定義：`src/lesson-registry.mjs` の `figures` に書き、`rendererRef: 'code:<名前>'` で描画方法を指定する。
  - 実装：`src/figures/` に置き、`src/figures/figure-ref.tsx` に `rendererRef` を登録する。登録しないと描画されない。
- 定義には次を書く。
  - `educationalPurpose`：その図で何を確かめるか
  - `legend`：図の要素の意味
  - `altText`：図の内容を文章で述べたもの
  - 座標図（`kind: 'cartesian'`）では `variables`（変数と単位）と `axes`（軸・ラベル・尺度）
- **定義した内容が、実際の図に反映されていることを確かめる。** レンダラーが独自の説明や凡例を描く場合は、定義と画面の文言が一致しているかを見る。
- 図を見なくても同じ内容が分かるテキストを、本文か図の中に置く（判断順序の箇条書き、数値の表など）。
- **意味のある線と枠**（分岐線、判断の箱、軸、基準線、読み取りに使うグリッド）は、Light と Dark の両方で、隣接する色とのコントラストを 3:1 以上にする。装飾の枠は対象外。
- 320px の画面幅でも読めるようにする。幅に応じて配置を変えてよい。
- 帯・棒・点が、軸の範囲に収まるようにする。収まらない値を扱う場合は、範囲を超えたことが分かる表示にする。端の値を検算する（例：平均 ± s の帯は、中心値を含めて「100 ± 2 mm」と書き、帯の両端が軸に収まるか確かめる）。
- 図が本文と別の例を使う場合は、図の前でそのことを書く。

### 4.1 操作できる図

- キーボードで操作でき、フォーカスが見えるようにする。マウスとタッチでも操作できるようにする。
- 操作した結果を、数値でも確かめられるようにする。
- 初期状態に戻す操作を用意する。
- 操作した結果は保存しない場合、そのことを本文に書く。

## 5. 演習

### 5.1 演習のデータ

演習は共通スキーマ（`ExerciseQuestion`、`src/lesson-contract.d.mts`）で定義する。

```
display:
  prompt            問題文
  table             表（1つ、または複数の配列）。セルは数値か文字列
  calculations      解答前に表示する式（任意）
  response          numeric（入力欄）または choice（選択肢）
  reviewSectionRefs 復習先の節
evaluation:         正答
solution:
  steps             途中式・判断の手順
  explanation       まとめ
  choiceFeedback    選択肢ごとの誤答説明と復習先
```

型の上では `table`、`calculations`、`steps`、`choiceFeedback` は省略でき、`reviewSectionRefs` は空でもよい。執筆するときは、次を**必ず**書く。

| 項目 | 必ず書く場合 |
|---|---|
| `display.reviewSectionRefs` | 常に1つ以上（型の上では必須だが、空の配列も通る） |
| `display.table` | 表を読んで解く問題すべて。表題（`caption`）と列見出し（`columnLabels`、`rowHeaderLabel`）も問題のデータに持たせる。表示画面で補わない |
| `solution.steps` | 計算か、2段階以上の判断を要する問題 |
| `solution.choiceFeedback` | 選択式の問題で、正答以外のすべての選択肢 |
| `choiceFeedback[].reviewSectionRefs` | 各誤答説明に1つ以上（型の上では省略も空の配列も通る） |

- **問題に必要な表は、演習の `display.table` に持たせる。** 本文の表を「上の表」と参照しない。説明に必要な表は本文に残し、演習には本文と別のデータの表を置く。
- **問題文に、解くための前提をすべて書く。** 結論を出すのに必要な範囲で、次を書く。
  - 検査した範囲と記録の対象（例：「検査した5個をすべて、1製品1行で記録しました」）
  - 抜き出した記録なら、何を全部載せたか（例：「基準を超えた傷をすべて載せた明細です」）
  - コードの意味と判定基準（例：「0＝適合、1＝不適合」、「基準を超えた傷が1件以上ある製品を不適合品とします」）
- **本文の例と演習のデータは別にする。** 本文で答えまで示した例を演習に使うと、答えを先に見せることになる（例：本文は P-01〜P-04、演習は Q-01〜Q-05）。生成する問題では、並べ替えたものも含めて、本文のデータが出ないことを確かめる。

### 5.2 解答前に見せないもの

【必須】解答前に表示される場所（問題文、表題、列見出し、`display.calculations`）に、**学習者に求める結果や判断**を書かない。

選択肢は、答えの候補なので、結果と理由を書いてよい。ただし、**どれが正答かを明かす手掛かり**（正答だけが長い・詳しい、誤答が自分の誤りを述べる、など）を入れない（5.3 節）。

- 例：観測単位を問う演習・事例の表題に「（1行＝傷1件）」を書かない。学習者には、列名や製品番号の重複から判断してもらう。表題には、何を記録した表か（例：「基準を超えた傷の明細」）だけを書く。
- 集計の結果や、正答につながる判断の過程は `solution` に置く。

次は、解答前に見せてよい。
- 問題を解く材料として与える式（例：誤計算を診断する問題で、誤りを含む計算過程を示す）
- `solution` の内容。解説は最初は閉じておく。
  - 採点前：学習者が自分で開いたときだけ表示する（学習者の選択として認める）。
  - 採点後：正答のときは自動で開いてよい。誤答のときは自動で開かず、誤答説明と復習先を示す。

### 5.3 選択肢の品質

選択式の問題は、次をすべて満たすようにする。

- [ ] 選択肢の長さと詳しさがそろっている（正答だけが長い・詳しい状態にしない）
- [ ] 選択肢が同じ観点を同じ順序で述べている（例：「不適合品の数え方 → 不適合の数え方」の順を全選択肢でそろえる）
- [ ] 複数の観点（例：分類と、その理由）を組み合わせる場合は、全選択肢で観点の数と順序をそろえる。正答だけが理由を述べる状態にしない
- [ ] 誤答の選択肢に、自分が誤りだと分かる文言を入れない（例：「逆の単位で答える」）
- [ ] 正答がいつも先頭にならない。問題ごとに正答の位置を変える
- [ ] 誤答は、実際に起こりうる誤り（観測単位の取り違え、集計対象の取り違え、単位の取り違え、手順の誤りなど）に対応している
- [ ] 数値と手順の両方を書いた選択肢では、書かれた手順をそのとおり実行すると、その選択肢の数値になる
- [ ] 「数は正しいが理由が誤っている」選択肢を入れる場合は、問題文で「数と理由（数え方）の両方が正しいもの」を問う。数だけを問うと正答が複数になる。誤った手順を実行しても、その数値になること（例：「明細の1行は製品1個を表すので、2行を不適合品2個として数える」は、重複のない明細では実際に2になる）
- [ ] 与えられた情報だけから、正答が1つに決まる
- [ ] 誤計算の診断では、何を「誤り」と数えるかを問題文に書く（例：「前の行の値を使ったものとして、最初に誤った段階を選んでください」）

### 5.4 誤答説明と解説

- 誤答説明（`choiceFeedback`）は、**その選択肢の数え方や判断のどこが誤りか**を述べる。解答者が何を考えたかを決めつけない。
  - 良い例：「この選択肢は、見つかった傷がある製品をすべて不適合品として数えています。P-02とP-05の傷は基準内です。」
- 数値入力で、誤答の理由をシステムが区別できない場合は、理由を決めつけず、正しい考え方と確認する箇所を示す。
- 誤答説明には、復習先の節（`reviewSectionRefs`）を付ける。
- `steps` には途中式または判断の手順を、`explanation` には何を確かめた問題かのまとめを書く。途中式を `explanation` にまとめて書かない。

### 5.5 事例の組み立てと生成

- 1つの概念を確かめるときは、**対照になる事例をそろえる。**
  - 例：同じデータを別の形式で記録した事例。製品記録と傷明細のどちらでも、不適合品2個・不適合4件になる。記録形式だけが違うことを解説で示す。
  - 例：数が偶然一致する事例。傷明細の行数と不適合品数が、どちらも2になる。結果は同じでも、数える対象が違うことを確かめる。
- 事例は `index` で切り替えられるようにする。事例の数と範囲（`minimum` / `maximum`）は、本文のつなぎの文と一致させる。
- 計算中心の演習は、パラメータを変えて多数の問題を生成する（`seed` または `index`）。
- **問題は、定義 ID・`revision`・生成方式（`fixed` / `index` / `seed`）・入力値で識別する。** この4つが同じなら、常に同じ問題・正答・解説を返す。カテゴリや演習の並び順を変えても、識別子と出る問題は変わらない。
- 表示用のデータ（`display`）と、採点・解説用のデータ（`evaluation`・`solution`）は、別々に取り出す。最初の問題表示では、正誤と解説を表示しない。採点するとき、と学習者が解説を自分で開くとき（5.2 節）には、採点・解説用のデータを使ってよい。取り出したデータは複製して返し、画面側で書き換えても元の定義が変わらないようにする。
- **1回の出題**は、問題が表示されてから、別の問題に変わるか、画面を離れて戻れなくなるまでとする。「演習に戻る」で、元の問題と記録済みの状態を元に戻せた場合は、同じ1回の出題が続いているとみなす。元に戻せず演習を初期状態で表示した場合は、新しい出題とみなす（その後の最初の有効な採点を新しく記録する）。
- 採点の記録（独立演習の採点履歴）には、1回の出題につき最初の有効な採点だけを残す。未回答と入力形式の誤りは記録しない。同じ出題で答え直しても、記録は置き換えない。「演習に戻る」で元の出題を復元できた場合は、採点結果と「記録済み」の状態も元に戻し、二重に記録しない。初期状態で表示した場合は、上の定義のとおり新しい出題として扱う。
- 節の中の演習は、採点の記録に残さない（画面上の採点だけ）。
- 数値入力では、丸めの指示と、丸めの境界の値の採点を確かめる。複数の入力欄があるときは、全体が正解になる条件をはっきりさせる。

## 6. 導線

| 操作 | 期待する動き |
|---|---|
| マップの「解説を読む」 | 中間ページを通らずに、その単元の解説へ移る |
| マップの「教材一覧」の節リンク | その節の見出しへ移り、フォーカスする |
| 節へのリンク・URL 直接入力（同じタブでのハッシュ変更を含む） | その節の見出しへ移り、フォーカスする |
| 戻る・進む・再読み込み（有効な履歴があり、戻すのに必要な状態もそろっている） | 前に読んでいた位置と状態に戻る |
| 演習から復習先へ移る | 復習先の節の見出しへ移る。見出しの近くに「演習に戻る」を置く |
| 「演習に戻る」（元の演習の状態がそろっている） | 元の演習の問題（事例・seed）、入力、採点結果、記録済みの状態を元に戻し、元の復習リンクにフォーカスする |
| 「演習に戻る」（復習先を再読み込みしたなどで、元の演習の状態が欠けている） | 元の演習の画面へ戻り、演習を初期状態で表示して、下の手順4のフォーカス先へ移る。エラーにはしない |
| 復習先からさらに別の節を復習する（入れ子） | 戻るたびに、1段ずつ元の位置と状態に戻る |
| 戻る・進む・再読み込み（履歴がない、または戻すのに必要な状態が欠けている） | URL から画面を作り直す。演習の状態が欠けている場合は、その演習を初期状態で表示し、下の手順4のフォーカス先へ移る。エラーにはしない |

どの動きにするかは、次の順で決める。
1. **表にある操作を先に特定する。** 「演習に戻る」や「解説を読む」のように表に行がある操作は、その行のとおりにする。「演習に戻る」は、元の演習の状態がそろっていれば元の復習リンクへ、欠けていれば手順4のフォーカス先へ移る。
2. 表にない、画面内のリンクや URL 入力で新しく移った → 移った先の節の見出しへフォーカスする。
3. 戻る・進む・再読み込みで、有効な履歴があり、**戻すのに必要な状態もそろっている** → 記録した位置と状態を戻す。
4. 履歴がない、または必要な状態が欠けている → URL から画面を作り直し、次へフォーカスする。
   - 節の中の演習：その演習のある節の見出し
   - 独立演習：問題の見出し。問題を特定できなければ、独立演習のページの見出し

節の URL は、現在は単元ごとに形式が違う。
- 一般の単元：`#/lesson/<lessonId>/<sectionId>`（例：`#/lesson/data-types/counting`）
- 基本統計量：`#/course/descriptive-statistics/lesson/<sectionId>`

新しい単元は、一般の単元の形式を使う。

独立演習の画面から復習へ移る場合も、上の表と同じ動きにする。

## 7. 出典

- 学習者向けの出典は `references` に書く。本文の末尾に段落として書かない。
- 各出典（`references` の1項目）に、次を書く。
  - `title`：資料名（資料を特定できる版・節・ページを含める）
  - `url`：資料を直接開ける URL（サイトのトップページで済ませない）
  - `details`：照合した内容と確認日（例：「計量値・計数値・カテゴリの区別を照合。確認日：2026-11-20。」）
- 確認日は用途で書き分ける。公式出題範囲の台帳として資料を確認した日は `sources` の `checkedAt` に、教材の内容を資料と照合した日は `references` の `details` に書く。同じ資料を両方の用途で使う場合は、両方に書く。
- 転載・翻案はしない。例と設問は独自に作成したと書く。
- 外部のコードや素材を使ったときは、ライセンスとクレジットを単元の `credit` に書く。

## 8. 互換性と revision

### 8.1 互換性

- **正式リリースまで**は、後方互換性を考えない。`sectionId`、参照、route、保存データは、新しい構成に合わせて直してよい。
- ただし、保存データの入力検証、破損データのエラー処理、保存に失敗したときの扱いは、今の動きを保つ。
- 既存の ID・route・スキーマを守ることを理由に、教材の品質を下げない。スキーマや導線が教材の要求を満たせない場合（例：演習の表に文字列を入れられない、節へ直接移れない）は、同じ PR で拡張・修正する。

### 8.2 revision を上げる条件

revision は、**変わった出力**で決める。実装のファイルを共有しているかどうかでは決めない。1つの変更が複数の行に当たる場合は、当たる行の revision をそれぞれ上げる。

| 変わった出力 | 上げる revision |
|---|---|
| 本文（文言・表・式・図の定義）、`overview`、`references` | 教材の `revision` |
| 学習目標 | 教材の `revision` |
| 演習の `display`（問題文・表・選択肢・復習先）、`evaluation`（正答）、`solution`（解説・誤答説明・その復習先）、生成の範囲 | その演習の `revision`（問題の識別子が変わる） |
| 図の描画結果（レンダラーの変更で、図の内容や文言が変わった） | その図を載せている教材の `revision` |
| **構造**：節の追加・削除・分割・統合、`sectionId` の変更、節の並べ替え、単元の追加・削除、前提の参照先（単元・節）の変更、前提の追加・削除、任意の復習（`optionalReviews`）の参照先の変更・追加・削除 | 影響を受ける教材の `revision` と `curriculumRevision` |
| 保存データの形式 | その形式が使うバージョン番号（`revision` とは別。移行か破棄の方針を PR に書く） |

- 生成器やレンダラーを共有している場合も、出力が変わった演習・教材だけを上げる。
- 復習先（`reviewSectionRefs`）だけを直した場合も、演習の `revision` を上げる。

- 前提の参照先を変えた場合（例：`data-types` を `data-types#types` に変える）は構造の変更とし、参照する側の単元の `revision` と `curriculumRevision` を上げる。
- 単元を削除した場合は、`curriculumRevision` と、その単元を参照していた単元の `revision` を上げる。
- 保存データのバージョン番号は形式ごとに違う。例：学習の進捗と採点の記録は `schemaVersion`、バックアップファイルの外枠とブラウザの履歴は `version`。

## 9. 検証

PR を出す前に、次を確認する。確認していない項目を「確認済み」にしない。

- 9.1 節の `npm run build` は、リポジトリ全体に対して必ず実行する。
- それ以外の項目は、その PR の変更箇所と、変更が影響する範囲に対して確認する。付録 C などに記録済みの既知の違反は、10章と同じ条件（今回の変更で悪化させた場合、または同じ箇所にある場合）でだけ対象にする。

### 9.1 自動の確認

- [ ] `npm run build` が成功する（`npm run check`〔型検査とテスト〕を含む）
- [ ] 次のテストがある：問題の生成と再現性、採点（丸めの境界・複数欄を含む）、復習リンク、節への移動、演習への復帰（入れ子を含む）
- [ ] 生成する問題について、次を生成器とは別の計算で確かめるテストがある
  - 固定問題と、`index` で選ぶ問題（事例の切り替えを含む）：全件
  - `seed` で生成する問題：生成の分岐をすべて通る代表例、範囲の境界、反例になりやすい値
  - `seed` で生成する問題が本文のデータを出さないこと：代表例ではなく、全入力に効く方法で確かめる（生成器の除外条件を検証する、または生成されうる値の組をすべて列挙して本文と比べる）

### 9.2 画面の確認

対象：画面の表示や操作が変わりうる PR。本文・演習・図・導線・スキーマ・表示の CSS を変えたら対象になる。ドキュメントやテストだけの変更は対象外とし、PR に「画面への影響なし」と書く。

- [ ] production preview で、1280px と 320px、Light と Dark の4条件すべてで、表示（はみ出し、横スクロール、表、図、コントラスト）を確認した
- [ ] 次の操作を、少なくとも1つの条件で確認した。該当する要素がないものは「該当なし」と書く（どの項目でも同じ）
  - キーボード操作とフォーカス表示
  - 「もっと正確に」の開閉
  - 事例の切り替え、採点、復習からの復帰（入れ子を含む）
  - 操作できる図の、キーボード・マウス・タッチでの操作と初期化
- [ ] 図の意味のある線・枠のコントラストを確認した（図がない場合は「該当なし」と書く）
- [ ] 図の帯・棒・点が軸の範囲に収まるか、超える場合は超過が分かる表示になっていることを確認した（図がない、または軸のない図では「該当なし」と書く）
- [ ] 実際のブラウザで、人が見て確認した

画面の確認は、PR に短く記録する：対象のコミット SHA、ブラウザ、幅、テーマ、操作と結果。

### 9.3 内容の確認

- [ ] 5.3 節の選択肢チェックリストを満たす（対象の範囲は 9.1 節の生成問題の確認と同じ）
- [ ] 演習のデータが本文の例と別で、解答前に表示される場所に、求める結果や判断がない（5.2 節）
- [ ] 演習の問題文に、解くための前提がすべて書かれている（5.1 節）
- [ ] 「必ず」「常に」「〜にならない」などの言い切りに反例がない。確率・推定の主張に抽出の条件がある
- [ ] 用語・単位・識別子の表記が、本文・表・選択肢・解説でそろっている
- [ ] 本文と演習の数値、正答、誤答説明、`steps` を、実際のコードと照らし合わせて検算した（演習の対象の範囲は 9.1 節と同じ）

## 10. レビュー

- 実装担当とは別のレビュー担当が、このガイドラインに照らしてレビューする。
- 指摘には must-fix / should-fix / nit を付ける。
- **レビューの対象は、その PR の変更箇所と、変更が影響する範囲**とする。付録 C などに記録済みの既知の違反は、今回の変更で悪化させた場合か、今回の変更と同じ箇所にある場合だけ指摘する。それ以外は合否に含めない。
- **合格**は、対象の範囲に must-fix と should-fix が残っていない状態。nit だけが残る場合は合格とする。nit を直すかは PR の作成者が決め、迷うときはリポジトリの所有者に聞く。
- 1回のレビューは、1つのコミットを対象に、完了したレビュー結果1件と数える。同じコミットを再依頼したり、並行して複数のレビュー担当に依頼したりした場合は、まとめて1回と数える。
- 合格するまで、修正とレビューを繰り返す。5回で合格しなければ、いったん止める。残った指摘とこれまでの経緯をまとめて、リポジトリの所有者に判断を仰ぐ。
- レビューで見つかった、このガイドラインにない観点は、PR に記録してガイドラインに追加する。
- レビューの記録は、指摘・対応・残課題に絞る。記録のための表や様式を増やさない。2.1 節の理由や 9.2 節の画面確認の記録は、これとは別に書く。

- 観測単位を「表の1行」と定義した文言（P2-01）は、解説HTMLのたたき台が元になっている。v0 7.2 はむしろ「観測単位を決めてから分類する」と正しく書いていた。
- 「同じ6製品の傷明細」の事例を削除したこと（P2-04）は、実装の指示による。
- 「傷明細で合計しても不適合品数にならない」という言い切りは、たたき台と実装の文言から来たもので、v0 の記述からではない。

ガイドラインを直すだけでは、たたき台を作る段階の誤りは防げない。たたき台を作るときにも、3章と 9.3 節の内容チェックを使う。
